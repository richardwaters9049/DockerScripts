# AGENTS.md

## Purpose and scope

This repository contains Bash generators for disposable, Docker-based development and operations environments. The important distinction is that most of the code under `scripts/` is **code that writes other code**. A change inside a heredoc changes a future generated project; it does not automatically update an already-generated example under `projects/`.

These instructions apply to the repository root and all descendants unless a more specific `AGENTS.md` exists. Several generated frontend projects contain their own `AGENTS.md`; use the closest file when working inside one of those trees.

The repository currently has three generator families:

1. `docker_pyNext`, `docker_pyNext_v2`, and `docker_pyNext_v3` generate a small Next.js + FastAPI + Prisma + PostgreSQL stack.
2. `bootstrap-ai-platform.sh` generates a larger Next.js + FastAPI + SQLAlchemy + PostgreSQL starter with a polished dashboard and team-note flow.
3. `docker_infraOps` generates an infrastructure operations lab containing metrics, logs, alerts, synthetic traffic, object storage, and backup/restore tooling.

The checked-in directories under `projects/` are examples, smoke-test outputs, or working snapshots. They are useful for understanding the result of a generator, but they can drift from generator source.

All root scripts are stored with a non-executable Git mode, so documentation and tests should invoke them explicitly with `bash`, for example `bash scripts/docker_pyNext_v3 demo`. Do not assume `./scripts/docker_pyNext_v3` works after a fresh clone.

## Generator summary

| Generator | Backend/data layer | Frontend | Main purpose | Startup behavior |
| --- | --- | --- | --- | --- |
| `scripts/docker_pyNext` | FastAPI, Prisma Client Python, PostgreSQL | Next.js generated by Bun | Original compact starter, including users/training patterns | Builds and starts Compose |
| `scripts/docker_pyNext_v2` | Same base as v1 | Adds Framer Motion/CLSX users dashboard | UI-enhanced legacy variant | Builds and starts Compose |

| `scripts/bootstrap-ai-platform.sh` | FastAPI, SQLAlchemy, Psycopg, PostgreSQL 15 | Next.js, Tailwind, Framer Motion, reusable UI components | Larger application/dashboard starter | Always builds, starts, and waits for health checks |

The versioned `docker_pyNext` files are independent snapshots, not wrappers around one shared implementation. Do not apply a change to all versions automatically. Preserve legacy behavior unless a task explicitly asks for parity. New functionality normally belongs in v3 and, when applicable, in its Docker Hub packaging.

## `docker_pyNext_v3`: current compact full-stack generator

Run it from the directory that should contain the new project:

```bash
bash scripts/docker_pyNext_v3 my-app
```

### Inputs and environment controls

| Name | Default | Meaning |
| --- | --- | --- |
| First positional argument | none | Project directory. Required unless `PROJECT_NAME` is set. |
| `PROJECT_NAME` | empty | Environment fallback for the project directory. Primarily used by the Docker image. |
| `NON_INTERACTIVE` | `0` | Set to `1` to avoid overwrite prompts. |
| `EXISTING_PATH_MODE` | `overwrite` | In non-interactive mode: `overwrite`, `keep`, or `delete`. |
| `SKIP_DOCKER_UP` | `0` | Set to `1` to generate files without running Compose. |
| `SKIP_FRONTEND_CREATE` | `false` | Internal/advanced switch that bypasses `bun create next-app`. Existing frontend handling can also set it. |

Be careful with the project name and existing-path mode. The script passes paths to `rm -rf` and does not enforce a safe basename. Use a simple relative name such as `my-app`; never test destructive modes against a valuable directory, an absolute path, `.` or `..`.

### Generated backend

The script writes:

- `backend/.env` with a Compose-network PostgreSQL URL.
- `backend/requirements.txt` with FastAPI, Uvicorn, Prisma, pytest, pytest-asyncio, HTTPX, and multipart form support.
- `backend/Dockerfile`, based on Python 3.11 and explicitly pinned to `linux/amd64`.
- `backend/prisma/schema.prisma` with a `User` model.
- `backend/app/database.py` containing one shared async `Prisma` client.
- `backend/app/main.py` with lifespan connection retry, CORS, `/`, `GET /users`, and form-based `POST /users` routes.
- `backend/app/hooks/user_hooks.py` with database access and HTTP error mapping.
- `backend/seed.py`, which idempotently upserts Alice, Bob, and Charlie by email.
- `backend/app/tests/test_users.py` and `backend/pytest.ini`.

The generated API stores passwords as plain text. It is demonstration scaffolding only. Do not describe it as production-ready authentication, and do not place real credentials in it. A production adaptation needs password hashing, validation, secret management, migrations, authorization, and tighter error handling/CORS.

### Generated frontend

The generator runs `bun create next-app` with TypeScript, Tailwind, ESLint, the App Router, and the `@/*` alias, then installs dependencies. It replaces the home page with a client-rendered users dashboard. The browser calls `NEXT_PUBLIC_API_BASE_URL`, falling back to `http://localhost:8000`, and animates user cards with Framer Motion.

Because the API call happens in the browser, the public API URL must be host/browser reachable. It should not normally be changed to the Compose hostname `backend`, which resolves inside the Docker network but not in the user's browser.

### Runtime sequence

The generated Compose file defines `db`, `backend`, and `frontend`:

1. PostgreSQL starts and reports readiness via `pg_isready`.
2. The backend waits on the healthy DB, regenerates the Prisma client, runs `prisma db push --accept-data-loss`, seeds users, and starts Uvicorn with reload enabled.
3. The Bun container installs frontend packages and starts the Next.js development server.
4. The generator checks that all three services are running and tests TCP connectivity from backend to `db:5432`.

Default host ports are fixed: PostgreSQL `5432`, backend `8000`, and frontend `3000`. Unlike `docker_infraOps`, this generator does not search for free ports.

`prisma db push --accept-data-loss` is convenient for disposable development data but can make destructive schema changes. If evolving this into a durable application template, prefer checked-in Prisma migrations and remove `--accept-data-loss`.

### Existing-directory behavior

The script handles `backend` and `frontend` separately after entering the project directory:

- **Overwrite** deletes and recreates the selected directory.
- **Keep** keeps the directory, although subsequent unconditional file writes can still replace individual backend/config files. “Keep” does not mean the entire project is immutable.
- **Delete** removes the directory and may leave it absent if the user declines recreation; later writes can then fail under `set -e`.

Non-interactive `delete` removes without recreating. Treat this mode as an advanced/destructive option rather than a normal generation mode.

## Docker Hub wrapper for v3

`Dockerfile.dockerhub` builds a small CLI image from `docker:27-cli`, installs Bash and Bun, copies `docker_pyNext_v3`, and sets `/workspace` as the working directory. Its defaults are intentionally automation-friendly:

```text
NON_INTERACTIVE=1
EXISTING_PATH_MODE=overwrite
WORKSPACE_ROOT=/workspace
```

`dockerhub-entrypoint.sh`:

1. applies the non-interactive defaults;
2. creates a `docker-compose` shim that delegates to `docker compose` when the legacy command is absent;
3. changes to `/workspace`;
4. converts `PROJECT_NAME` into the positional argument when no argument was supplied; and
5. `exec`s the v3 generator.

To scaffold onto the host, mount the target directory at `/workspace`. To let the generated project start sibling containers, also mount `/var/run/docker.sock`. Mounting the Docker socket grants the generator effectively root-level control over the host Docker daemon; call this out in examples and never assume it is safe in an untrusted environment.

Typical safe scaffold-only smoke run:

```bash
docker build -f Dockerfile.dockerhub -t docker-pynext:local .
mkdir -p /tmp/docker-pynext-smoke
docker run --rm \
  -e PROJECT_NAME=smoke \
  -e SKIP_DOCKER_UP=1 \
  -v /tmp/docker-pynext-smoke:/workspace \
  docker-pynext:local
```

If `Dockerfile.dockerhub`, the entrypoint, or v3 interface/defaults change, review all three files plus the Docker Hub section of `README.md` together.

## `bootstrap-ai-platform.sh`: larger application starter

Run:

```bash
bash scripts/bootstrap-ai-platform.sh my-platform
```

If no name is provided, the directory defaults to `synextra-ai-starter`. An existing directory makes the script stop unless `FORCE=1`; with `FORCE=1` it recursively deletes and rebuilds that directory.

Supported environment overrides are:

- `FRONTEND_PORT` (default `3000`)
- `BACKEND_PORT` (default `8000`)
- `POSTGRES_PORT` (default `5432`)
- `POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD` (all default `synextra`)
- `FORCE=1` for destructive replacement

This generator uses strict Bash mode (`set -euo pipefail`). It captures noisy build command output in temporary files and prints it on failure. Its `wait_for` helper polls backend and frontend HTTP endpoints for up to 150 seconds, then emits Compose status and recent service logs.

### Application generated by the bootstrapper

The backend uses synchronous SQLAlchemy and Psycopg rather than Prisma. It creates tables at startup and seeds two model types:

- `StarterModule`: categorized starter capabilities, ownership, stage, tags, and display order.
- `TeamNote`: a database-backed note with author, title, message, lane, and creation time.

The API surface is:

- `GET /` — API identity/status.
- `GET /health` — database-backed health/count response.
- `GET /api/overview` — application summary, metrics, modules, and notes.
- `POST /api/team-notes` — validated note creation.

The frontend is a composed dashboard with UI primitives, dashboard sections, typed API functions, a service layer, React hooks, tests, and `/demo`. It uses Bun, Next.js, TypeScript, Tailwind, Framer Motion, Lucide icons, CLSX, Tailwind Merge, and Class Variance Authority.

Compose builds separate frontend/backend Dockerfiles and starts PostgreSQL. Generated helper targets are available through `make up`, `make down`, `make typecheck`, `make frontend-test`, and `make backend-test`.

Unlike v3, this generator has no scaffold-only switch and uses `docker compose` directly. A full invocation requires Docker to be running, Bun on the host, network access for packages/images, and the configured ports to be free.

## `docker_infraOps`: operations lab generator

Run and start:

```bash
bash scripts/docker_infraOps my-infra-lab
```

Generate only:

```bash
bash scripts/docker_infraOps my-infra-lab --no-start
```

The generator detects `docker compose` and falls back to `docker-compose`. When startup is requested on macOS and the daemon is stopped, it attempts to open Docker Desktop and waits up to three minutes.

It checks the preferred localhost ports and chooses the next available port in a short range, with a random free-port fallback. Selected values and randomly generated Grafana, MinIO, and Restic secrets are written to the generated `.env`; `.env.example` contains placeholders. The generated `.gitignore` excludes `.env`, backups, data, and logs.

### Generated services

| Service | Role | Default host exposure |
| --- | --- | --- |
| Prometheus | Scrapes metrics and evaluates alert rules | `127.0.0.1:9090` |
| Alertmanager | Routes alerts to Mailpit email | `127.0.0.1:9093` |
| Grafana | Provisioned Prometheus/Loki dashboards | `127.0.0.1:3000` |
| Loki | Local log storage | Internal only |
| Vector | Reads Docker logs and ships them to Loki | Internal; mounts Docker socket |
| Blackbox Exporter | HTTP probes for demo app and Grafana | Internal only |
| Demo app | Python metrics endpoint and deliberate 5% failure rate | `127.0.0.1:8088` |
| Load generator | Continuously requests the demo app | Internal only |
| Mailpit | Captures alert email; SMTP also uses fixed port 1025 | UI `127.0.0.1:8025` |
| MinIO / `minio-init` | S3-compatible storage and private Restic bucket | API `9000`, console `9001` |
| Restic | Profile-gated backup/restore tool | `tools` profile only |
| cAdvisor | Optional container CPU/memory metrics | `extras` profile; privileged |

Most exposed ports bind only to loopback. Preserve that security property unless remote access is an explicit requirement. Note that SMTP port `1025` is fixed and is not included in the generator's dynamic port selection.

Prometheus scrapes itself, cAdvisor, the demo app, and blackbox probes. The supplied rules alert when the demo app is unavailable or its 5xx rate is high. Grafana is provisioned with Prometheus and Loki data sources plus panels for availability, probes, errors, latency, resource use, and demo logs. Vector needs `/var/run/docker.sock`, and cAdvisor needs privileged host mounts; both deserve explicit security review outside a local lab.

### Generated operations helpers

The large generator embeds each helper below as a heredoc. The corresponding files under `projects/infraops-lab/scripts/` are a checked-in generated copy.

| Helper | Behavior |
| --- | --- |
| `up.sh` | Loads `.env`, resolves port collisions, pulls/builds, starts services, and reports URLs. |
| `down.sh` | Runs Compose down without deleting named volumes. |
| `pull-images.sh` | Pulls pinned images with exponential retry; `--extras` includes cAdvisor. |
| `cache-images.sh [path] [--extras]` | Pulls then saves images to a Docker archive for constrained networks. |
| `smoke-test.sh` | Checks demo app, Prometheus readiness, and Grafana health with `curl`. |
| `demo.sh` | Runs an incident drill, including stopping/restarting the demo app and observing alert state. |
| `triage-bundle.sh` | Captures versions, service state, health, and recent logs under `backups/`. |
| `capacity-report.sh` | Queries Prometheus for top container CPU and memory consumers. |
| `backup-init.sh` | Initializes the Restic repository in MinIO if needed. |
| `backup.sh` | Backs up mounted data/config, then applies daily/weekly/monthly retention and prune. |
| `restore-latest.sh` | Restores the latest snapshot beneath `backups/restore-latest`. |

Generated `docs/` contains a runbook, service catalog, and postmortem template. Keep those documents aligned with service names, ports, alert timing, and operational helper behavior.

### Source/output synchronization rule

For an InfraOps change, decide which artifact the task targets:

- To change future generated labs, edit the heredoc inside `scripts/docker_infraOps`.
- To fix only the checked-in lab, edit `projects/infraops-lab/...`.
- If the checked-in lab is intended to demonstrate the current generator, update both the generator heredoc and generated file, then verify they are semantically identical.

Never edit only the generated copy and imply the generator was fixed. Conversely, regenerating over `projects/infraops-lab` is destructive and can overwrite local `.env`, secrets, backups, or user modifications. Inspect `git status` first and use a temporary output directory for comparison.

## Heredoc and shell editing conventions

These scripts intentionally contain large heredocs. Quoting determines when variables expand:

- `<<'EOF'` writes content literally. Variables such as `${PORT}` remain in the generated file for runtime expansion.
- `<<EOF` expands variables while the generator runs. Use it for values intentionally baked into output.
- A heredoc terminator must start at column 1 and match exactly.

When adding generated shell, YAML, Python, or TypeScript, remember that it has two contexts: the outer generator and the generated program. Escape `$`, backticks, quotes, and backslashes for the correct layer. Prefer quoted heredocs unless generation-time substitution is required.

Other conventions:

- New standalone Bash scripts should use `#!/usr/bin/env bash` and normally `set -euo pipefail`.
- Preserve compatibility with the Bash shipped by macOS when modifying InfraOps helpers; do not require Bash 4-only associative arrays or `mapfile` without a documented reason.
- Quote variable expansions and paths. Use `read -r`.
- Prefer `docker compose`, but retain the existing fallback helper where a generator supports legacy `docker-compose`.
- Pin infrastructure image versions in the generated `.env`/Compose defaults. When changing a pin, update image pull/cache lists and docs together.
- Keep generated services on the shared Compose network and refer to them by service name internally.
- Preserve named volumes unless a task explicitly requires destructive reset semantics.
- Do not silently weaken loopback bindings, authentication, bucket privacy, or secret generation.
- Avoid adding real secrets, credentials, tokens, customer names/data, or machine-specific absolute paths.
- Do not hand-edit Bun lockfiles for dependency changes; let Bun regenerate them in a disposable/generated project.

## Validation strategy

Choose validation proportional to the change. A full generator run downloads packages, builds images, creates directories, starts containers, reserves ports, and may modify Docker state, so do not use the repository root as the output location for a smoke test.

### Minimum checks for any shell change

```bash
bash -n dockerhub-entrypoint.sh
bash -n scripts/docker_pyNext
bash -n scripts/docker_pyNext_v2
bash -n scripts/docker_pyNext_v3
bash -n scripts/bootstrap-ai-platform.sh
bash -n scripts/docker_infraOps
```

If `shellcheck` is installed, run it on the changed standalone script. Expect deliberate warnings around sourced `.env` files, dynamic Compose invocation, and heredoc-generated code; suppress only a specific, understood warning near the affected line.

### Scaffold-only checks

For v3, generate into a disposable directory without starting Docker:

```bash
tmpdir="$(mktemp -d)"
(
  cd "$tmpdir"
  NON_INTERACTIVE=1 EXISTING_PATH_MODE=overwrite SKIP_DOCKER_UP=1 \
    bash /absolute/path/to/DockerScripts/scripts/docker_pyNext_v3 smoke-app
)
```

This still invokes Bun and accesses the network. Inspect the resulting Compose config with:

```bash
cd "$tmpdir/smoke-app"
docker compose config --quiet
```

For InfraOps, use `--no-start` from a disposable directory, then validate the generated YAML and generated shell scripts:

```bash
tmpdir="$(mktemp -d)"
(
  cd "$tmpdir"
  bash /absolute/path/to/DockerScripts/scripts/docker_infraOps smoke-lab --no-start
  cd smoke-lab
  docker compose config --quiet
  for file in scripts/*.sh; do bash -n "$file"; done
)
```

The InfraOps generator is still interactive if the target exists, so always use a new temporary path.

The AI bootstrapper has no no-start mode. A true generation test is also an integration test and should be run only when Docker/Bun/network use is acceptable:

```bash
tmpdir="$(mktemp -d)"
(
  cd "$tmpdir"
  FRONTEND_PORT=3100 BACKEND_PORT=8100 POSTGRES_PORT=55432 \
    bash /absolute/path/to/DockerScripts/scripts/bootstrap-ai-platform.sh smoke-platform
)
```

Afterward, run `docker compose down -v` inside the disposable generated project if data preservation is not needed.

### Generated application checks

For a v3 output:

```bash
docker compose exec backend pytest -q
curl -fsS http://localhost:8000/users
curl -fsS http://localhost:3000 >/dev/null
```

For an AI platform output:

```bash
make backend-test
make typecheck
make frontend-test
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8000/api/overview
```

For an InfraOps output:

```bash
bash scripts/smoke-test.sh
docker compose config --quiet
```

Run the longer `demo.sh`, backup, restore, image-cache, or cAdvisor checks only when the change affects those workflows. They alter runtime state, can take several minutes, and may consume significant disk/network resources.

## Change checklist

Before finishing a change:

1. Inspect `git status` and preserve unrelated user changes; generated projects commonly contain local work and secrets.
2. Identify whether the task concerns a generator, a generated snapshot, or both.
3. Review every heredoc boundary touched and run `bash -n` on the outer generator.
4. If generated shell changed, generate into a temporary directory and run `bash -n` on that output too.
5. Validate generated Compose with `docker compose config --quiet` when YAML, variables, services, volumes, ports, or profiles changed.
6. Keep image pins synchronized between Compose, `.env`, `.env.example`, `pull-images.sh`, and `cache-images.sh`.
7. Keep public docs synchronized with command names, defaults, URLs, endpoints, and prerequisites.
8. Call out any validation not run, especially Docker builds, network downloads, destructive drills, or backup/restore tests.

## Common pitfalls

- Running a generator from the repository root can create or overwrite a top-level project directory.
- `FORCE=1`, non-interactive overwrite/delete, and interactive overwrite all call `rm -rf`.
- v3's `Keep` path mode does not prevent later unconditional writes.
- Fixed ports in the full-stack generators collide easily with existing local services.
- `linux/amd64` platform declarations may use emulation on Apple Silicon and can slow builds.
- The Docker Hub wrapper needs the host Docker socket to launch its generated Compose stack.
- The v3 backend uses schema push with data-loss acceptance, not a migration history.
- Generated dev servers use reload mode and bind mounts; they are development setups, not deployment definitions.
- InfraOps Vector sees Docker metadata through the daemon socket; cAdvisor runs privileged with host mounts.
- InfraOps alert rules intentionally take time (`for` durations), so an alert drill is not an instant assertion.
- Backups are stored in MinIO, while restore output and triage bundles use the generated `backups/` directory; do not commit either secrets or backup artifacts.
- `NextPY-Docscript.md` documents older behavior and may mention routes removed from v3. Confirm behavior from the actual generator before updating user-facing claims.

## Documentation expectations

`README.md` should remain concise and user-oriented. Put maintainer mechanics, generation layers, synchronization rules, and validation details here. When behavior changes, update the nearest relevant documentation:

- root usage or recommended generator: `README.md`;
- generator maintenance rules: this `AGENTS.md`;
- generated InfraOps operation: the embedded docs in `docker_infraOps` and, when maintained in sync, `projects/infraops-lab/docs/`;
- generated frontend conventions: the closest frontend `AGENTS.md`/`README.md`.

Use current filenames and `bash scripts/...` commands in examples. State clearly whether a command scaffolds only or also starts containers.
